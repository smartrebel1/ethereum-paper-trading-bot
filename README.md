# ETHUSDT Paper Trading Engine — Phase 1

A deterministic, **paper-only** trading research engine for ETHUSDT.
The engine runs **entirely locally (or on your own server)**: no GitHub, no CI
and no cloud service is involved in running, testing or scheduling it. If you
keep the project in Git it is only as a backup of the code — see ADR-020 and
the Arabic note in [`START_HERE_AR.md`](START_HERE_AR.md).

> **Live trading is not implemented — and cannot be, by construction.**
> `TradingMode`/`ExecutionProvider` have no `LIVE` member, the startup guard
> exits with code 2 on any unsafe configuration, and the database rejects any
> order or execution row whose provider is not `'paper'`
> (`ck_orders_paper_only`, `ck_executions_paper_only`).

## Quick start

**Just want to run it?** → `bash scripts/start.sh` (one command: safety check →
migrations → ingest → replay → dashboard → server) and open
<http://127.0.0.1:8000/dashboard>. A plain-Arabic walkthrough lives in
[`START_HERE_AR.md`](START_HERE_AR.md) (Windows: `start.bat`).

Or step by step:

```bash
python3.12+ -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env

python scripts/check_env.py       # effective config + safety report (exit 2 if unsafe)
python scripts/ingest_archive.py  # validate + store the Binance archive (idempotent)
python scripts/replay.py          # replay the whole series through the paper engine
python scripts/render_dashboard.py  # write dashboard/dashboard_ar.html (Arabic panel)

# Continuous paper mode (public Binance market data; no API keys; never places orders)
python scripts/run_paper_scheduler.py
# one tick only:
python scripts/run_paper_scheduler.py --once

uvicorn app.main:app --host 127.0.0.1 --port 8000
#   dashboard : http://127.0.0.1:8000/dashboard           (Arabic, plain language)
#   technical : http://127.0.0.1:8000/dashboard/technical (tables + audit trail)
#   api docs  : http://127.0.0.1:8000/docs
#   health    : /health  /ready  /version  /metrics  /metrics/prometheus

pytest                          # 279 tests, ~20s, no network, no external services
ruff check . && ruff format --check .
```

One command from nothing to a full backtest, entirely offline:

```bash
python scripts/replay.py --rebuild-db --report data/replay_report.json
#   ingest 19,794 candles (3s) → replay 2017-08-17 → 2026-08-31 (~4 min)
```

`make help` runs the same commands through the bundled `Makefile`.

### Data tables (16)

`candles` · `signals` · `orders` · `executions` · `positions` · `trades` ·
`portfolio_snapshots` · `strategy_versions` · `risk_decisions` · `system_events` ·
`integrity_events` · `ai_observations` · `data_sources` · `scheduler_runs` ·
`health_checks` · `configuration_versions`

Two invariants live in the database, not just in code:

* `uq_positions_one_open_per_sym_tf` — partial unique index: at most one `OPEN`
  position per `(symbol, timeframe)`.
* `ck_signals_target_after_candle` — a signal's `target_execution_open_time` must
  be strictly after its own candle: same-candle fills are unrepresentable.

## HTTP surface

Read-only by design — **there is no write endpoint**, so mounting the API cannot
change trading state. Trading state is driven by candle arrival, never by HTTP.

| Endpoint | Purpose |
|---|---|
| `GET /` | content negotiation: browsers → `/dashboard`, tools → JSON index |
| `GET /health` | liveness, no DB access (works before `init_db`) |
| `GET /ready` | safety + database + schema checks |
| `GET /version` | software/strategy identity |
| `GET /metrics`, `GET /metrics/prometheus` | JSON metrics / Prometheus gauges |
| `GET /dashboard` | **Arabic** plain-language panel: what we bought, when it executed, profit, next expected trade |
| `GET /dashboard/technical` | operational/technical view (tables, audit trail) |
| `GET /api/v1/dashboard/summary` | the panel's numbers as JSON (same values, machine-readable) |
| `GET /api/v1/config` | frozen strategy + hash + coverage + safety report |
| `GET /api/v1/status` | counts, pipeline state, integrity criticals |
| `GET /api/v1/{candles,signals,orders,trades,events,integrity}` | paginated history |
| `GET /api/v1/positions/open`, `/portfolio/latest`, `/portfolio/equity` | position + equity curve |

Before `init_db`: `/health` answers, `/ready` reports `ready: false`, and
`/api/v1/*` returns **503** with the exact fix command instead of a stack trace.

## Continuous Integration

GitHub Actions now runs on every push to `main` and every pull request targeting
`main`. The CI gate uses Python 3.12 and checks:

- `ruff check .`
- `ruff format --check .`
- `pytest`

The workflow is defined in [`.github/workflows/ci.yml`](.github/workflows/ci.yml).
It does not connect to Binance, execute trades, or require secrets.

## Continuous paper mode

Run `python scripts/run_paper_scheduler.py` on your own machine/server to keep the paper engine advancing as new closed candles appear. The scheduler:

- polls the public Binance REST market-data endpoint only;
- refuses incomplete candles;
- persists validated candles idempotently;
- rebuilds the EMA/ATR warm-up window without replaying historical side effects;
- processes each new candle exactly once using the existing risk and paper-execution path;
- records scheduler heartbeats in `scheduler_runs` and resumes from the last successful candle after a restart;
- stops on a critical execution-target integrity failure instead of inventing a substitute fill.

Binance documents public market-data endpoints for market data; this project uses them only for candles, never for order submission.

## Cloud dashboard from mobile

The repository includes a Render Blueprint in `render.yaml` for a public web dashboard plus a continuous paper-trading worker backed by PostgreSQL.

### Deploy

1. Open Render and create a Blueprint from this repository.
2. Select `smartrebel1/ethereum-paper-trading-bot`.
3. Deploy the Blueprint.
4. After the web service is live, open:
   `https://<your-service>.onrender.com/dashboard`

The worker runs `scripts/run_cloud_worker.py`, initializes migrations, imports the public historical Binance archive when the database is empty, rebuilds paper-trading history when needed, and then runs the continuous closed-candle scheduler.

**Safety:** this deployment remains paper-only. It does not accept Binance API keys and has no live-order execution path.

**Important hosting note:** Render currently does not offer a free Background Worker. The Blueprint therefore uses the smallest paid worker plan for continuous scheduling; the free web service and free PostgreSQL options have separate limitations, including the free Postgres 30-day expiry. For a permanently free always-on setup, use a VM instead.

See the official Render Blueprint documentation for the current deployment flow.
